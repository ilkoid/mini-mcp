# Обследование базы 1С «PLM» (sql02.office.playtoday.ru) — доступ и ландшафт, 2026-09-26

Часть 1 серии. Конфигурация 1С ещё не выгружена (ждём от разработчиков);
задача этой части — понять, что можно извлечь из самой базы, и открыть
доступ. **Состояние: обследование подготовлено полностью, доступ к базе
`plm` заблокирован на стороне сервера; ниже точная причина и готовый
скрипт починки.**

## 1. Резюме

| Что | Статус |
|---|---|
| Транспорт обследования | ✅ готов: одноразовый Go-раннер `plm-survey/` (вне git) |
| Сервер найден и опознан | ✅ SQL02, default instance, SQL Server 2019 Standard |
| Список баз на сервере | ✅ получен (см. §3) — целевая база называется **`plm`** |

| Windows-аутентификация | ❌ VPS не в доверенном домене (18452) |

## 2. Хронология разведки доступа (все секреты остались в `.env`/env.cmd)

Креды по условию лежат в `.env` (переменные `PLM_SQL_NAME`, `PLM_SQL_IP`,
`PLM_RO_USER`, `PLM_RO_USER_PWD`); значения нигде не печатались —
проверялись только длина/класс символов/отсутствие `\r`/не-плейсхолдер.

1. **Прямой SQL-логин `plm_reader`** (Go-раннер на драйвере go-mssqldb):
   отвергнут ошибкой **18456** на обоих адресах сервера. Контроль: с
   корректным паролем и недоступной базой ошибка была бы 4064, а не 18456 →
   дело не в имени базы, а в самом логине (нет/отключен/другой пароль).
   Перебор initial catalog (`-db PLM/plm/PLM_1C/…`) ничего не изменил —
   версия с contained-user тоже отпала (база `plm` проверялась).
2. **SQL Browser (UDP 1434)**: `ServerName=SQL02, InstanceName=MSSQLSERVER,
   tcp=1433, Version=15.0.2000.5` — порт и инстанс угаданы верно, на обоих
   DNS-адресах (192.168.5.79 и 10.120.11.24) отвечает один и тот же сервер.
3. **Windows integrated (SSPI)**: 18452 «untrusted domain» — VPS не
   доменный, путь отпадает.
4. **Linked server с DWH**: на DWH обнаружен линк `SQL02 →
   sql02.office.playtoday.ru` (провайдер MSOLEDBSQL). Через него читается
   `master` (список баз получен), но выполнение запроса к `[plm]` падает
   за 56 мс ошибкой **916**: линк авторизуется на SQL02 серверным логином
   **`fbs`**, которому не выдан доступ к базе `plm`. Загадочные «4-минутные
   таймауты» через MCP-таймауты — это те же отказы, просто в неудачной
   форме запроса.
5. **NTLM с явными AD-кредами** (`AD_USER`/`AD_USER_PWD` из `.env`, формат
   `office\kashparov.i`; драйвер go-mssqldb, провайдер
   `authenticator=ntlm`, машина в домене не нужна): домен **`office`
   распознаётся сервером** (варианты `PLAYTODAY\…`/`playtoday\…` дают 18452
   «untrusted domain», а `office` доходит до финальной проверки), но сам
   логин `office\kashparov.i` отвергнут с **18456** и на SQL02, и на DWH.
   Внешне неразличимы два случая: пароль в `.env` устарел, либо для личной
   учётки просто **не создан login ни на одном из серверов** (оба —
   бэкенды, личные доменные учётки аналитиков туда обычно не прописаны).
   UPN-форма `kashparov.i@playtoday.ru` NTLM не принимает (нужен
   `ДОМЕН\пользователь`).
6. Итог по серверу из `master` (линк читает): **SQL02, 15.0.4410.1
   (SQL Server 2019), Standard Edition (64-bit), mixed mode включён.**

Вывод: сеть до сервера есть, SQL-логины сервер принимает — не хватает
только валидного логина с правами чтения на `plm`. Решение:
`role-bootstrap-plm-mssql.sql` (создать/включить `plm_reader`, дать
`db_datareader` на `[plm]`, тот же пароль положить в `.env`).

## 4. Готовая инфраструктура обследования

- **`plm-survey/` (Go, вне git)** — раннер одного SELECT-батча:
  `set -a; source .env; set +a; go run ./plm-survey -db plm -q "SELECT …"`.
  Флаги: `-t` таймаут, `-max-rows`, `-max-cell`, `-integrated`, `-browser`.
  Проверен вживую против DWH (быстрые итерации, 56–83 мс).
- После починки логина обследование идёт с этой же VPS-машины напрямую
  (не через линк): линк годен только на `master` и вдобавг непрозрачно
  работает под чужим логином `fbs`.
- **Почему Config-извлечение пойдёт через раннер, а не через MCP**:
  контейнер конфигурации 1С — `VARBINARY`, а MCP-сервер справедливо
  блокирует бинарную выдачу (binary guard, Д-2). Прямой раннер под
  `plm_reader` с SELECT-only дисциплиной — правильный путь.

## 5. План обхода после открытия доступа (этапы 2–5 исходного плана)

1. **Инвентаризация** — гистограмма `sys.tables` по 1C-префиксам
   (`_Reference` справочники, `_Document` документы, `_InfoRg` регистры
   сведений, `_AccumRg` регистры накопления, суффикс `_VTNN` — табличные
   части) + топ-30 таблиц по строкам/МБ (`sys.dm_db_partition_stats`),
   маркеры `Config`/`Params`.
2. **Идентификация сущностей** — `TOP 5 _Description` крупнейших
   справочников (Номенклатура, Сезоны, Размеры…), документы по
   `MIN/MAX(_Date_Time)`, ключи/ресурсы регистров.
3. **Связи** — все колонки `*_RRef binary(16)` как кандидаты M:1 с
   выборочной валидацией джойном на `_IDRRef`; `_VT` — 1:N от владельца;
   граф в mermaid.
4. **Карта имён из `Config`** — выгрузка контейнера (FileName/PartNo/Data),
   распаковка deflate-блоков, соответствие «таблица ↔ объект метаданных
   (русские имена)». Фолбэк — выгрузка конфигурации от разработчиков.
5. **Отчёт части 2** — глоссарий сущностей, топ-таблицы, граф связей,
   что подтвердить выгрузкой.

Дисциплина безопасности: только SELECT; `READ UNCOMMITTED`/`NOLOCK` на
таблицах данных; TOP-ограничения; без семплирования личных данных
(`_Author` и пр.); сервер — рабочая 1С, всё «лёгкое».
