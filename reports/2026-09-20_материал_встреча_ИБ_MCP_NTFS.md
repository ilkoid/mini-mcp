## 1. Что предлагается (коротко)

Агент ZCode (внутренний ИИ-ассистент аналитиков) получает возможность
**искать файлы** на файл-серверах компании (имя, путь, даты, размер,
владелец, отдел, теги папок) и **получать выбранный файл** в свой локальный
кеш для анализа — как если бы пользователь сам открыл его в проводнике.

Чего **нет** принципиально: записи/перемещения файлов (система навсегда
read-only), чтения содержимого файлов на этапе индексации (только метаданные
ФС и списки доступа), какого-либо «супер-доступа» от имени сервиса.

Компоненты:

| Компонент | Где | Что делает |
|---|---|---|
| ntfs-agent (сервис) | каждый файл-сервер | читает USN-журнал NTFS и MFT, собирает метаданные, шлёт батчами в хаб |
| ntfs-hub (сервис) | сервер ZCode | единственный писатель индекса (SQLite, локальный диск); обогащение из AD |
| mcp-ntfs (процесс ZCode) | сессия пользователя | поиск + выдача файлов; работает **под учёткой пользователя** |

## 2. Физика процесса

### Контур индексации (фон, без пользователей)

1. На файл-сервере включается USN-журнал (стандартный механизм NTFS, ведёт
   сама файловая система) и ставится сервис-агент под LocalSystem.
2. Первичный проход: перечисление MFT — скелет тома (имена, идентификаторы,
   атрибуты) за минуты на миллионы файлов.
3. Проход метаданных: для каждого файла — размер, даты, владелец (SID),
   дескриптор безопасности (DACL). Пулом воркеров, в фоне. Содержимое не читается.
4. Записи уходят батчами по HTTP в хаб (внутренний LAN, токен). Хаб пишет в
   SQLite, обновляет полнотекстовый индекс, запрашивает воcстановление
   профиля владельца из AD, подтверждает батч — только после подтверждения
   агент двигает курсор журнала (идемпотентность, рестарты без дублей и дыр).
   Соединения инициируют только агенты — исходящие на сервер ZCode:8733; на
   файл-серверах не открывается ни одного входящего порта, а сама база SQLite
   по сети не доступна в принципе — файл пишет только локальный процесс хаба.
   Источник данных маркирован: каждая строка связана с корнем (файловый
   сервер + том), и агент может писать только в «свои» корни — по
   персональному токену, выданному хабом.
5. Дальше — режим ожидания: раз в ~30 с агент читает новые записи журнала.
   Создание/удаление/переименование/**смена ACL** обрабатываются по флагам
   причин, т.е. индекс отстаёт от файловой системы максимум на интервал
   опроса. Еженедельно — контрольный полный перескан.

### Клиентский путь (пользователь → файл в руках агента)

1. ZCode запускает mcp-ntfs **под учётной записью вошедшего пользователя** —
   процесс наследует его токен (группы, права), а не права сервиса.
2. Агент вызывает поиск (ключевые слова / маска / фильтры).
3. Кандидаты выбираются из локального индекса (миллисекунды, по сети не ходим).
4. **Фильтр доступа:** каждая строка-кандидат проверяется локально —
   сохранённый DACL файла сверяется с токеном пользователя (право чтения на
   файл + право листинга на все родительские папки). Недоступное
   отбрасывается молча: ни имени, ни факта существования. Любая ошибка
   проверки трактуется как «нет доступа».
5. Агент запрашивает конкретный файл. Путь обязан существовать в индексе —
   произвольные пути вне проиндексированных корней не принимаются.
6. **Жёсткая граница:** файл открывается по SMB под учёткой пользователя —
   файл-сервер применяет реальный NTFS ACL и права шары. Нет прав →
   ACCESS_DENIED, даже если строка случайно попала в выдачу из-за
   устаревшего DACL.
7. Файл копируется в персональную временную папку пользователя
   (`%LOCALAPPDATA%\Temp\...` — изолирована по построению), с лимитом
   размера; факт выдачи пишется в журнал аудита. Агент анализирует уже
   локальную копию; после — TTL-очистка.
8. Что идёт по сети: только метаданные-батчи (килобайты) и байты
   запрошенных файлов на шаге 6–7. Никакого фонового выкачивания содержимого.

## 3. Модель разграничения доступа (главное требование)

**Индексация с полными правами, чтение индекса — в пределах прав пользователя.**

| Слой | Механизм | Что гарантирует |
|---|---|---|
| Поиск | DACL-фильтр по индексу: `AccessCheck` против токена процесса пользователя (локально, без сети) | пользователь не видит в поиске НИ имени, ни факта существования недоступных файлов |
| Выдача | реальное SMB-открытие под учёткой пользователя | авторизация файл-сервером по полному стеку: NTFS ACL + права шары; сервисной учёткой файлы не открываются никогда |
| Отказоустойчивость | deny-by-default (нет/кривой DACL, ошибка проверки → скрыть); отставание индекса закрывается границей выдачи | при любом сбое фильтра утечки содержимого не происходит — худший случай это ACCESS_DENIED |
| Аудит | `fetch_audit`: кто, что, когда, размер, статус | полный след выдач файлов |

Осознанные ограничения (просим согласовать): share-ACL и центральные политики
доступа в индексе не моделируются — поиск может показать строку, которую
«через шину» не открыть; это перекрывается границей выдачи. DACL в индексе
свежий с точностью до USN-события (секунды-минуты).

## 4. Что индексатор собирает — и чего не собирает

| Собирает (метаданные ФС, доступно любому с READ_CONTROL) | НЕ собирает |
|---|---|
| имя, путь, расширение, признак каталога | содержимое файлов (текст, картинки, данные) |
| размер, время создания/изменения, атрибуты | альтернативные потоки, 8.3-имена |
| владелец: SID + из AD — логин, ФИО, отдел, почта, активен | историю изменений, «кто последним правил» (NTFS это не хранит) |
| дескриптор безопасности (DACL) — для фильтрации поиска | SACL, хэши содержимого, превью |

## 5. Тезисы для ИБ

1. **Индексатор не читает содержимое** — только метаданные файловой системы
   и списки доступа; всё собираемое ОС и так отдаёт любому субъекту с правом
   READ_CONTROL.
2. **Выдача файла идёт под учёткой самого пользователя**, а не сервисной —
   серверная авторизация происходит штатным путём, отдельного
   «супер-доступа» не возникает.
3. **Поиск не раскрывает недоступного**: DACL-фильтр скрывает сам факт
   существования; при сбое фильтра выдачу остановит файл-сервер; кто/что/
   когда брал — в журнале аудита.

## 7. Глоссарий

### NTFS и USN-журнал

| Термин | Что это |
|---|---|
| **NTFS** | Файловая система Windows; метаданные каждого файла хранятся в служебных структурах тома |
| **MFT** (Master File Table) | Главная таблица файлов тома: одна запись = один файл или папка; перечисление MFT даёт весь том без обхода каталогов |
| **FRN** (File Reference Number) | 64-битный идентификатор записи MFT; стабильнее имени — переживает переименование и перемещение |
| **USN** (Update Sequence Number) | Монотонно растущий номер изменения на томе |
| **USN Change Journal** | Системный файл тома ($UsnJrnl), куда NTFS **сама** пишет запись о каждом изменении: создание, удаление, запись данных, переименование, смена ACL |
| **USN Record / Reason flags** | Запись журнала (идентификаторы, имя) и флаги причин события: `CREATE`, `DELETE`, `RENAME_OLD/NEW`, `DATA_OVERWRITE`, `ACL_CHANGE` и др. |
| **Wrap журнала** | Переполнение журнала по кругу: старые записи затираются → требуется полный перескан; лечится размером журнала |
| **Tombstone** | «Надгробие»: строка индекса с пометкой об удалении файла, хранится ограниченный срок |

### Безопасность Windows / AD

| Термин | Что это |
|---|---|
| **SID** | Идентификатор безопасности (S-1-5-…): пользователя, группы, компьютера; уникален в домене |
| **Owner SID** | Владелец файла, по умолчанию — создатель; при создании с повышенными правами (UAC) владельцем становится Administrators |
| **SD** (Security Descriptor) | Блоб безопасности объекта: Owner SID + Group SID + DACL + SACL; именно он сохраняется в индексе |
| **DACL / ACE** | Список, кто и что **может** делать с объектом; ACE — одна запись (тип, маска прав, SID) |
| **SACL** | Список обращений, которые логируются системным аудитом (мы не используем) |
| **Access token** | Токен процесса: SID пользователя + группы + привилегии; MCP-процесс наследует токен самого пользователя |
| **AccessCheck** | Windows API: сверка токена с дескриптором безопасности — локально, без сети |
| **FILE_READ_DATA / FILE_LIST_DIRECTORY / FILE_TRAVERSE** | Право читать файл / видеть содержимое папки / проходить сквозь папку; правило видимости: READ на файле + LIST на всех предках |
| **READ_CONTROL** | Право читать чужой дескриптор безопасности — нужно индексатору |
| **AD / LDAP / bind** | Active Directory; LDAP — протокол запросов; bind — служебная учётка подключения |
| **LocalSystem** | Системная учётка сервиса-агента на файл-сервере (читает весь том — это его работа) |
| **SSPI / NTLM / Kerberos** | Механизмы встроенной Windows-аутентификации — вариант для канала агент→хаб |

### Сеть и стек

| Термин | Что это |
|---|---|
| **SMB** | Протокол доступа к файлам по сети (шары `\\сервер\папка`) |
| **UNC-путь** | Канонический сетевой путь `\\fs01\photo$\...` |
| **Share-level ACL** | Отдельный слой прав на шару ПОВЕРХ NTFS-прав; в индексе не моделируется, применяется файл-сервером при выдаче |
| **SQLite / WAL** | Встраиваемая БД в одном файле; WAL — режим «один писатель + много читателей» без взаимных блокировок |
| **FTS5 / GLOB** | Полнотекстовый поиск по именам (понимает кириллицу) / поиск по маске `*паттерн*` |
| **MCP / stdio** | Model Context Protocol — протокол подключения инструментов к агенту; stdio — запуск как процесс ZCode с обменом через стандартные потоки |
