## 1. Контекст

Сервис отдаёт результаты read-only SQL с анонимизацией: чувствительные ключевые
слова (пример: реальный бренд компании) заменяются алиасами (пример алиаса:
`FamilyMegaBrand`), а алиасы в SQL-литералах запроса транслируются обратно в
реальные значения. Сторонние бренды (Disney и т.п.) не маскируются — словарь,
по-видимому, закрывает только собственные чувствительные значения.

Тестирование показало: базовые сценарии маскируются корректно, но есть три
группы проблем:

1. **Утечки** — производные от чувствительных значений (подстроки, хэши, длины)
   проходят в выдачу без маскировки.
2. **Целостность аналитики** — соответствие «значение → алиас» не инъективно:
   два разных реальных значения схлопываются в один алиас, из-за чего GROUP BY
   показывает дубли, а фильтры по алиасу молча теряют строки.
3. **UX** — `=` по алиасу молча возвращает 0 строк (описание инструмента это
   обещает, но не гасит).

**Предполагаемая архитектура** (уточнить при разборе): замена выполняется
пост-обработкой текста результата и текста запроса по *полному вхождению*
ключевого слова. Из этой архитектуры следуют все деекты ниже: всё, что не
совпадает с ключевым словом «целиком» (префикс, хэш, длина), не заменяется.

Тестовый стенд: таблицы `public.cards` (33 325 строк, 10 значений бренда),
`public.sales` (2 484 139 строк), `public.search_queries_daily` (свободный текст
`search_text`). Все примеры воспроизводимы через `pg_readonly_query`; реальные
значения в этом ТЗ и в отчёте замаскированы — при воспроизведении вы увидите их
сами.

## 3. Дефекты и задачи

Приоритет: **P1** — утечки, **P2** — корректность аналитики, **P3** — UX/документация.

### Д-1 (P1). Подстрочные функции раскрывают фрагменты реальных значений

**Воспроизведение** (возвращает реальные первые 4 символа бренда без маскировки):

```sql
SELECT left(brand, 4) AS p4, count(*) FROM cards GROUP BY 1 ORDER BY 2 DESC
```

**Класс проблема.** Замена срабатывает только на полное вхождение ключевого
слова, поэтому любая функция, возвращающая *часть* значения или его
*трансформацию*, обходится. Зафиксировано для `left`; тот же принцип работает
для: `right`, `substring`/`substr`, `split_part` (для многословных значений),
`btrim`/`ltrim`/`rtrim`, `overlay`, `lpad`/`rpad`, `regexp_replace`,
`regexp_matches`, `regexp_split_to_*`, `translate`, `reverse`, `initcap`,
`string_to_array` + обращение к элементу, а также boolean-оракулы вида
`strpos(brand,'…') > 0`, `brand LIKE '…%'`.

**Требование.** В выдаче не должно оказаться производных реальных значений:
ни подстрок, ни трансформаций, ни boolean-оракулов по содержимому.

**Рекомендуемое решение (вариант A, основной).** Перейти от чёрного списка
функций к **белому списку выражений** над чувствительными колонками:

1. В MCP уже есть словарь ключевых слов → известно, какие колонки чувствительные
   (сейчас как минимум `cards.brand`, `sales.brand_name`, …). Если соответствие
   «колонка → словарь» не хранится — добавить (маппинг колонок на словари).
2. Статически разбирать SQL (парсер типа pg_query) и для каждой
   чувствительной колонки разрешать только:
   - вывод значения как есть (пост-обработка заменит его на алиас);
   - сравнения/фильтры литералами (`=`, `IN`, `LIKE`, `ILIKE`, `~`);
   - `GROUP BY` / `DISTINCT` / `ORDER BY`;
   - агрегаты счётчиков строк (`count(*)`, `count(col)`).
3. Любое другое выражение над чувствительной колонкой → отказ запроса с ошибкой
   вида: `функция left() неприменима к колонке cards.brand (ограничение анонимизации) — выберите колонку целиком или агрегат`.

Белый список закрывает весь класс, включая будущие функции и самодельные
оракулы (`CASE WHEN brand LIKE '_l__' THEN …`).

**Вариант B (запасной, если парсинг SQL внедрить нельзя).** Блок-лист функций
из списка выше по тексту запроса + маскировка в выводе подстрок ключевых слов
длиной ≥ 4 символов. Дешевле, но остаётся класс обходов через оракулы;
рассматривать как временный компромисс.

**Критерий приёмки.** Каждый запрос из списка ниже либо возвращает только
алиасные/замаскированные значения, либо отклоняется с понятной ошибкой; прямая
выборка (`SELECT brand`) продолжает работать:

```sql
SELECT left(brand, 4),  count(*) FROM cards GROUP BY 1;
SELECT right(brand, 4), count(*) FROM cards GROUP BY 1;
SELECT substring(brand from 1 for 4), count(*) FROM cards GROUP BY 1;
SELECT split_part(brand, ' ', 1), count(*) FROM cards GROUP BY 1;
SELECT btrim(brand, 'Fam'), count(*) FROM cards GROUP BY 1;
SELECT reverse(brand), count(*) FROM cards GROUP BY 1;
SELECT initcap(brand), count(*) FROM cards GROUP BY 1;
SELECT strpos(brand, 'Fam') > 0, count(*) FROM cards GROUP BY 1;
```

### Д-2 (P1). Крипто-хэши и кодирования проходят без маскировки

**Воспроизведение** (возвращает настоящие MD5-хэши реальных значений):

```sql
SELECT md5(brand) AS h, count(*) FROM cards GROUP BY 1 ORDER BY 2 DESC
```

**Требование.** В выдачу не должен попадать материал, позволяющий восстановить
реальное значение по словарю или сшить его с другой выгрузкой: `md5`, `sha224`,
`sha256`, `sha384`, `sha512`, `hmac`, `encode(col::bytea, 'hex'|'base64')`,
`convert_to`, любые самодельные хэши через побитовые операции.

**Решение.** В рамках белого списка из Д-1 — автоматически запрещено. Если
белый список не внедряется — блок-лист перечисленных функций над
чувствительными колонками. Соление хэша **не** подходит: стабильная соль даёт
тот же сопоставимый отпечаток, нестабильная ломает логику запроса.

**Критерий приёмки.** `SELECT md5(brand) FROM cards GROUP BY 1` и
`SELECT encode(brand::bytea,'base64') FROM cards GROUP BY 1` — отказ с
понятной ошибкой либо маска; в выдаче нет hex/base64-строк, кодирующих
реальные значения.

### Д-3 (P1). `length()` даёт отпечаток реальной длины

**Воспроизведение** (алиас из 15 символов идёт в паре с реальной длиной 9):

```sql
SELECT brand, length(brand) AS len, count(*) FROM cards GROUP BY 1, 2 ORDER BY 3 DESC
```

**Требование.** Для чувствительных колонок `length`, `char_length`,
`octet_length`, `bit_length` не должны раскрывать реальную длину.

**Решение.** Согласованная подмена: возвращать длину **алиаса** (то, что
пользователь видит в выдаче). Это сохраняет согласованность результата и не
даёт информацию о реальном значении. Альтернатива — блокировать (в рамках
белого списка Д-1 блокируется автоматически).

**Критерий приёмки.** `length(brand)` для строк с алиасом `FamilyMegaBrand`
возвращает 15 (длину алиаса) или запрос отклоняется; реальная длина (не равна
15) не фигурирует.

### Д-4 (P2). Соответствие «значение → алиас» не инъективно

**Воспроизведение:**

```sql
SELECT brand, count(*) FROM cards GROUP BY brand ORDER BY 2 DESC;
-- две строки с одинаковым алиасом FamilyMegaBrand: 31 463 и 1

SELECT brand_name, count(*) FROM sales GROUP BY brand_name ORDER BY 2 DESC;
-- две строки FamilyMegaBrand: 1 694 346 и 788 463

SELECT count(DISTINCT brand) FROM cards;   -- 10
-- при этом уникальных алиасов в выдаче GROUP BY — 9
```

Два разных реальных значения (длины 15 и 9 символов) схлопываются в один
алиас. Следствия: дубли строк в GROUP BY/`string_agg`; `count(DISTINCT …)` не
сходится с видимыми алиасами; фильтр по алиасу возвращает строки только одного
из значений (см. Д-5/проверку Б-2 протокола).

**Требование.**

1. Каждому реальному значению из словаря — **уникальный** алиас
   (`FamilyMegaBrand`, `FamilyMegaBrand2`, …), чтобы GROUP BY/DISTINCT были
   консистентны.
2. Пока инъективность не обеспечена (или если одно реальное значение имеет
   несколько написаний в данных — регистр/пробелы): обратный перевод алиаса в
   фильтрах должен разворачиваться во **все** реальные значения этого алиаса
   (`= ANY(...)` / `ILIKE ANY(...)`), чтобы фильтр не терял строки.
3. Разобраться с данными/словарём: похоже, либо в `cards`/`sales` лежит второе
   написание бренда, отсутствующее в словаре, либо в данных встречается сам
   алиас как значение (длина 15). Проверить и пополнить словарь либо вычистить
   тестовое значение.

**Критерий приёмки.**

- `GROUP BY brand` по `cards` не содержит двух строк с одинаковим алиасом;
- `count(DISTINCT brand)` = числу уникальных алиасов в выдаче GROUP BY;
- `SELECT count(*) FROM cards WHERE brand ILIKE 'FamilyMegaBrand'` = сумме
  строк всех значений, скрытых под этим алиасом (сейчас 31 463 вместо 31 464).

### Д-5 (P2). `=` по алиасу молча возвращает 0 строк

**Воспроизведение:**

```sql
SELECT count(*) FROM cards WHERE brand  =  'FamilyMegaBrand';  -- 0
SELECT count(*) FROM cards WHERE brand ILIKE 'FamilyMegaBrand'; -- 31 463
SELECT count(*) FROM cards WHERE brand  =  'Disney';            -- 107 (контроль: проходящее значение работает)
```

Причина: обратный перевод алиаса восстанавливает слово в написании, которое
может отличаться регистром от хранящегося в БД; `=` в PostgreSQL
регистрозависим. Сейчас это поведение обещано только текстом описания
инструмента — пользователь о нём не вспоминает и получает «пустой результат».

**Требование.** Семантика сравнения литерала-алиаса любым оператором (`=`,
`IN`, `LIKE`, `ILIKE`, `~`) должна совпадать с фильтром по реальному значению.

**Решение (одно из):**

1. При переводе литерала подставлять точное написание из БД: в словаре хранить
   варианты написания, транслировать в `= ANY(варианты)`;
2. Для чувствительных колонок переписывать `col = 'литерал'` в эквивалент
   `col ILIKE 'литерал'` (с учётом экранирования LIKE-метасимволов);
3. Минимум, если 1–2 не делаются: при 0 строк и наличии `=`-сравнения по
   алиасу добавлять в ответ `notice`: «фильтр по алиасу чувствительного
   значения: используйте ILIKE (регистр)».

**Критерий приёмки.** `=` и `ILIKE` по одному и тому же литералу-алиасу дают
одинаковый ненулевой результат (после Д-4 — полный, без потери строк).

### Д-6 (P3). Непоследовательный регистр замен

**Воспроизведение:**

```sql
SELECT upper(brand), count(*) FROM cards GROUP BY 1 ORDER BY 2 DESC;
-- 'FamilyMegaBrand' (31 463) и 'FAMILYMEGABRAND' (1) — два разных написания одного алиаса
```

Реальные значения не раскрылись, но замена выполняется по разным правилам для
разных вхождений.

**Требование.** Единое правило регистра, например: если заменяемый токен целиком
в верхнем регистре — алиас в верхнем регистре (`FAMILYMEGABRAND`), иначе —
каноническое написание алиаса (`FamilyMegaBrand`).

**Критерий приёмки.** Повторный прогон запроса выше даёт одно написание на
правило; оба варианта соответствуют правилу.

---

### Д-7 (P3). Частичные LIKE-шаблоны не транслируются (остаточный риск)

**Воспроизведение:**

```sql
SELECT count(*) FROM cards WHERE brand ILIKE '%Mega%';  -- 1: шаблон не транслируется, count-оракул по подстрокам
```

Полное закрытие невозможно без знания всех подстрок реальных значений — принять
как документированное ограничение.

**Требование (минимум).** Зафиксировать ограничение в описании инструмента.
**Опционально:** если LIKE-шаблон содержит ≥ 4 символа алиаса подряд —
добавлять `notice` о том, что шаблон по частичному совпадению может вести себя
неочевидно.

**Критерий приёмки.** Описание инструмента содержит ограничение; (опция)
notice появляется.
