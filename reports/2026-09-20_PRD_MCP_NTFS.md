# PRD: MCP NTFS — индексация и поиск файлов на файловых серверах

| | |
|---|---|
| **Кому** | разработчик mini-mcp (будущие `mcp-ntfs`, `ntfs-indexer`) |
| **От** | аналитика arm-ai (логин wsl) |
| **Дата** | 2026-09-20 |
| **Статус** | черновик v1; ключевые решения зафиксированы владельцем 2026-09-20 (§2) |
| **Затрагивает** | новый компонент репозитория mini-mcp: `cmd/mcp-ntfs`, `cmd/ntfs-indexer`, `internal/ntfs`; переиспользует `internal/result` (сразу) и `internal/anon` (v2) |

---

## 1. Цель и сценарии

Дать агенту ZCode два базовых действия над файловыми массивами компании:

1. **Поиск файлов** — по ключевому слову / паттерну имени, по атрибутам NTFS
   (даты, размер, владелец), по данным AD (отдел, ФИО владельца) и по
   семантическим тегам папок.
2. **Получение файла** — копия во временный локальный кеш ZCode для анализа
   (текст, PDF, изображение, эскиз) средствами самого агента.

Опорные сценарии (из исходной идеи владельца):

| # | Сценарий | Как закрывается в v1 |
|---|---|---|
| С-1 | Артикул — 8-значная строка, каждая цифра семантична. Найти папки/файлы товара по артикулу | `ntfs_search` по паттерну имени/пути (`*12345678*`), теги папок из YAML |
| С-2 | Фото по артикулу; вид съёмки закодирован в ПАПКЕ (предметка, лук на модели) | теги папок (`tags: [предметка, лук]`) — вычисляются при индексации из паттернов пути, фильтр в поиске |
| С-3 | Разрешительная документация (сертификаты, декларации) | поиск по имени/папке/тегу + `ntfs_fetch` PDF → pdf-инструменты ZCode; полнотекст по содержимому — v3 |
| С-4 | Эскизы Adobe Illustrator / PDF («понять, что за одежда») | `ntfs_fetch` + конвертация/анализ агентом (AI-файлы с PDF-совместимой основой читаются pdf-инструментами) |
| С-5 | Регламенты и инструкции (docx/pdf) | метаданные + fetch в v1; полнотекст — v3 |

**Не-цели v1:** извлечение содержимого файлов при индексации (EXIF, текст
PDF/DOCX — v2/v3), запись/перемещение файлов (сервер навсегда read-only),
NAS/SMB-корни без USN (v3), анонимизация (v2, отдельным этапом).

## 2. Зафиксированные решения (владелец, 2026-09-20)

| Вопрос | Решение | Следствие |
|---|---|---|
| Где работает индексатор | Локально на наших файл-серверах | Доступен USN-журнал: инкремент за секунды, удаления/переименования/ACL-изменения отслеживаются бесплатно; индексаторов несколько |
| Где лежит индекс | SQLite на ЛОКАЛЬНОМ диске сервера ZCode | Один файл базы, WAL, единственный писатель — hub на сервере ZCode; SQLite поверх SMB запрещён (локи/повреждение) |
| Скрытие недоступных файлов | Полное | Поиск фильтрует по DACL из индекса + жёсткая реальная проверка при выдаче файла; недоступных файлов в выдаче нет вообще |
| Объём v1 | Метаданные NTFS + теги папок из YAML | EXIF и полнотекст — v2/v3; схема расширения заложена (отдельные таблицы, без миграций) |
| Обогащение AD | Аккаунт + профиль: sAMAccountName, ФИО, отдел, почта, активен | Кэш-таблица `ad_cache`; фильтры «файлы отдела X», здравый поиск автора |
| Стек | Чистый Go: `modernc.org/sqlite` (FTS5 включён), `golang.org/x/sys/windows` | PowerShell — только ад-хок операции вручную, НЕ рантайм; SID→имя — `LookupAccountSid`, AD — LDAP при индексации |

## 3. Архитектура

```
[Файловый сервер FS01]                       [Сервер ZCode]
 ntfs-agent (сервис Windows)                 ntfs-hub (сервис Windows)
   MFT-скан + USN-журнал                HTTP  ┌─────────────────────────┐
   owner SID, DACL blob        ──батчи──►    │ единственный писатель   │
                                             │ SQLite (WAL, локально)  │──► index.db
[Файловый сервер FS02]                       │ LDAP→AD (ad_cache)      │
 ntfs-agent ─────────────────────────────►   │ теги папок из YAML      │
                                             └───────────┬─────────────┘
                                                         │ read-only (WAL-reader)
                                              mcp-ntfs (stdio, под учёткой
                                              пользователя ZCode) ◄──── ZCode
                                                │ 1) SQL-кандидаты
                                                │ 2) Authz-фильтр по DACL
                                                │    из индекса (локально)
                                                ▼
                                              SMB-открытие файла под учёткой
                                              пользователя → жёсткая граница
```

- **ntfs-agent** — по одному на файл-сервер. Читает локальные NTFS-тома:
  первичный проход через перечисление MFT (`FSCTL_ENUM_USN_DATA`), затем
  дельты USN-журнала (`FSCTL_READ_USN_JOURNAL`). Отправляет в hub батчи по
  HTTP с USN-курсором и квитированием (идемпотентно к рестартам).
- **ntfs-hub** — единственный писатель SQLite. Принимает батчи, обогащает AD,
  вычисляет теги, обслуживает схему/миграции. Agent и hub — **один бинарь
  `ntfs-indexer`** с флагом роли (`--role=agent|hub`).
- **mcp-ntfs** — stdio MCP-сервер, ZCode запускает его **под учёткой
  пользователя**. Читает базу read-only, фильтрует, копирует файлы в кеш.

**Граница безопасности** (зеркально правилу репозитория «граница — роль БД,
precheck — DX»): настоящая граница — **ACL файл-сервера**: выдача файла —
реальное SMB-открытие под учёткой пользователя, ОС не пустит. Фильтрация
поиска по сохранённому DACL — слой против утечки метаданных, не более.

**Направление трафика и маркировка источника:** все соединения инициируют
агенты — исходящие с файл-серверов на сервер ZCode, порт хаба (8733); на
файловых серверах не открывается ни одного входящего порта. База по сети не
доступна в принципе: файл SQLite пишет только локальный процесс хаба.
Каждая строка индекса маркирована источником:
`files.root_id → roots(agent, volume_guid)`.

## 4. Компонент: ntfs-agent

### 4.1 Что собирается (одна строка = один файл/папка)

| Поле | Источник |
|---|---|
| file id (FRN), parent FRN | USN-запись / MFT |
| имя, флаг каталога | USN-запись |
| размер, время создания/изменения, атрибуты | `OpenFileById` + `GetFileInformationByHandle` (проход метаданных с пулом воркеров) |
| owner SID, SECURITY_DESCRIPTOR (self-relative blob, OWNER+DACL+GROUP) | `GetSecurityInfo` тем же хендлом |
| путь | не хранится как факт — собирается из цепочки parent FRN при выдаче (в кеше агента frn→(parent,name)); в базу пишется собранный путь для поиска |

Первичный проход MFT даёт скелет (имена, FRN, атрибуты) за минуты на миллионы
записей; проход метаданных (открытия) — фоновый, скорость не критична (владелец:
терабайты, фоновый режим). Оценка: 4 системных вызова на файл, 8–16 воркеров.

### 4.2 Инкрементальность

- Поллинг USN-журнала (интервал конфигурируется, по умолчанию 10–30 с),
  курсор сохраняется в hub (квитирование батча), при рестарте агента —
  продолжение с последнего подтверждённого курсора, дубли подавляются
  UPSERT-ом по ключу.
- Причины USN: CREATE/DELETE → вставка/tombstone; RENAME_OLD+RENAME_NEW по
  FRN → переименование/перемещение; DATA_OVERWRITE/ATTRIB_CHANGE → обновление
  метаданных; **ACL_CHANGE → перевыгруз SD** (DACL в индексе всегда почти
  свежий — отдельного прохода по ACL не нужно).
- Полный рескан по расписанию (например, раз в неделю) — самовосстановление
  после wrap журнала; wrap детектируется по `USN_JOURNAL_DATA.NextUsn`/
  LowestValidUsn.

### 4.3 Ограничения и правила

- Только ЛОКАЛЬНЫЕ NTFS-тома файл-серверов; идентификация тома — Volume GUID
  path (`\\?\Volume{...}\`), не буква диска.
- Учётка агента — LocalSystem на файл-сервере (индексатор по определению
  читает весь том, включая READ_CONTROL на все файлы).
- Содержимое файлов агент НЕ читает (v1 — только метаданные; важно для
  восприятия владельцами данных).
- 8.3-имена и альтернативные потоки (ADS) не индексируются. Hardlink — один
  MFT-запись с несколькими именами: v1 дедуплицирует по FRN (последняя запись
  выигрывает), задокументировано; в фото-архивах hardlink'и практически
  не встречаются.

## 5. Компонент: ntfs-hub

- HTTP-листенер только для агентов: `POST /v1/batch` (батч записей + курсор),
  `GET /healthz`; firewall-правило — входящий порт только с IP файл-серверов.
  Аутентификация — **персональный токен на каждого агента** (env хаба):
  токен ↔ имя агента, и записи принимаются только в корни этого агента
  (root ownership — агент файл-сервера A не может писать в корни сервера B).
  Опция SSPI/NTLM — открытый вопрос О-1.
- **Маркировка источника:** каждая строка связана с корнем
  (`files.root_id → roots`), корень несёт имя файл-сервера (`agent`) и
  `volume_guid`; в выдаче поиска источник виден как префикс UNC-пути.
- Приём батча: одна транзакция UPSERT по `(root_id, frn)`, обновление FTS5,
  обновление `roots.usn_cursor` (= курсор батча) — квитирование.
- **AD-обогащение**: LDAP-запросы по незнакомым SID из батчей; кэш
  `ad_cache` с TTL (по умолчанию 7 дней): sAMAccountName, displayName,
  department, mail, активен/уволен. Денормализация в `files.owner_*` при
  приёме (join по кэшу), пересчёт владельцев при обновлении кэша.
- **Теги папок**: YAML-правила `path_pattern → [tags]` вычисляются при приёме
  для строк-папок; файл наследует теги ближайшей помеченной папки (папки —
  тоже строки индекса). Пример: `\\fs01\photo$\*предметка*\** → ["предметка"]`.
- Tombstone: удалённые строки помечаются `deleted_at` и хранятся настраиваемый
  срок (по умолчанию 30 дней) — база для v2-поиска «куда делся файл».
- Миграции схемы: `meta.schema_version`, применяются хабом при старте.

## 6. Схема данных (эскиз)

```sql
CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT);           -- schema_version и пр.

CREATE TABLE roots(
  id INTEGER PRIMARY KEY,
  agent TEXT NOT NULL,              -- имя файл-сервера
  volume_guid TEXT NOT NULL,        -- \\?\Volume{...}\
  unc_base TEXT NOT NULL,           -- канонический UNC для выдачи: \\fs01\photo$
  usn_cursor INTEGER NOT NULL DEFAULT 0,
  last_full_scan TEXT,
  file_count INTEGER,
  UNIQUE(agent, volume_guid)
);

CREATE TABLE files(
  root_id INTEGER NOT NULL REFERENCES roots,
  frn INTEGER NOT NULL,             -- file reference number (int64)
  parent_frn INTEGER NOT NULL,
  path TEXT NOT NULL,               -- собранный UNC-путь (уникален в корне)
  name TEXT NOT NULL,
  name_lower TEXT NOT NULL,         -- Unicode-нижний регистр (Go, не SQLite LOWER)
  ext TEXT,
  is_dir INTEGER NOT NULL DEFAULT 0,
  size INTEGER NOT NULL DEFAULT 0,
  ctime TEXT, mtime TEXT,           -- RFC3339
  attrs INTEGER,
  owner_sid TEXT,
  owner_sam TEXT, owner_display TEXT, owner_dept TEXT,  -- денормализовано из ad_cache
  tags TEXT,                        -- CSV тегов папок
  sd BLOB,                          -- SECURITY_DESCRIPTOR (self-relative)
  first_seen TEXT NOT NULL, last_seen TEXT NOT NULL,
  deleted_at TEXT,
  PRIMARY KEY(root_id, frn)
);
CREATE UNIQUE INDEX files_path ON files(root_id, path) WHERE deleted_at IS NULL;
CREATE INDEX files_parent ON files(root_id, parent_frn);
CREATE INDEX files_name_lower ON files(name_lower);

CREATE VIRTUAL TABLE files_fts USING fts5(name, tokenize='unicode61');  -- кириллица

CREATE TABLE ad_cache(
  sid TEXT PRIMARY KEY, sam TEXT, display TEXT, dept TEXT, mail TEXT,
  active INTEGER, fetched_at TEXT NOT NULL
);

CREATE TABLE fetch_audit(          -- кто/что/когда брал файл (см. §8)
  ts TEXT NOT NULL, user TEXT NOT NULL, root_id INTEGER NOT NULL,
  path TEXT NOT NULL, bytes INTEGER, status TEXT
);
```

Оценка объёма: ~0,5–1 КБ на строку (SD — основная масса); 5 млн файлов ≈
3–5 ГБ + ~0,5 ГБ FTS. SQLite это диапазон держит без проблем.

## 7. Компонент: mcp-ntfs (инструменты)

Все ответы — envelope `internal/result` (`{columns, row_count, truncated,
notice, rows}`, кэпы 4000 строк / 48 КБ, метаданные до строк). Stdout — только
MCP-фреймы; логи в stderr (правило репозитория). Аннотации `readOnly` с
`*bool` — как в `internal/pg/tools.go`.

### 7.1 ntfs_search

Параметры: `query` (ключевые слова — FTS5 MATCH по имени), `pattern`
(глоб по имени ИЛИ пути: `*12345678*`), `ext`, `size_min/max`,
`ctime_from/to`, `mtime_from/to`, `owner` (sAM/ФИО), `dept`, `tags`,
`is_dir`, `path_prefix`, `limit`, `offset`.

- FTS — `files_fts MATCH`; паттерн — `GLOB` по `name_lower`/`path`
  (регистронезависимость достигнута `name_lower`, т.к. SQLite LIKE/GLOB не
  понимают кириллицу); остальное — обычные предикаты + `path_prefix`.
- Кандидаты из SQL → **пост-фильтр доступа** (§8) → envelope.
- Колонки выдачи (узкие, под байтовый кэп): `path, name, ext, size, ctime,
  mtime, owner, dept, tags, is_dir`.
- В `notice` всегда — свежесть: возраст последнего USN-поллинга корней,
  попавших в выдачу (агент обязан знать, что индекс мог устареть).

### 7.2 ntfs_file_meta

Полная строка одного файла/папки по пути + сводка ACL (владелец, группа,
наследование, количество ACE — НЕ дамп SID'ов из DACL). Path-аргумент обязан
резолвиться в строку индекса, иначе ошибка «not in index».

### 7.3 ntfs_fetch

- Путь обязан существовать в индексе (canonical UNC из базы) — произвольные
  пути вне корней индексации не принимаются (анти-traversal).
- Копирование под учёткой пользователя (реальное SMB-открытие — жёсткая
  граница): отказ доступа = чистая ошибка ACCESS_DENIED с подсказкой.
- Режимы: `full` (лимит размера, по умолчанию 200 МБ, настраивается) и
  `preview` (первые N КБ / диапазон байт — для гигантских PDF/AI).
- Расхождение `mtime` файла с индексом → notice «файл изменён после
  индексации».
- Кеш: `%LOCALAPPDATA%\Temp\mcp-ntfs\<session>\` — изолирован per-user по
  построению; ответ: локальный путь + размер; далее агент читает файл
  штатными средствами (Read/pdf-скиллы).
- Запись в `fetch_audit` (лучше-усердно, не блокирует выдачу).

### 7.4 ntfs_cache_clear / ntfs_status

- `ntfs_cache_clear` — очистка кеша сессии (+фоновая TTL-уборка при старте
  процесса, TTL по умолчанию 24 ч).
- `ntfs_status` — по корням: счётчик файлов, USN-курсор, возраст последнего
  поллинга/полного рескана; состояние БД (schema_version). Для честности
  агента о свежести данных.

## 8. Разграничение доступа (главное требование)

**Правило видимости в поиске:** строка показывается пользователю, только если
для его токена выполняются одновременно:

1. `FILE_LIST_DIRECTORY` разрешено на ВСЕХ папках-предках (включая корень
   тома) — проверка по SD папок из индекса;
2. `FILE_READ_DATA` разрешено на самом файле.

**Механика (без сети, без имперсонации):** MCP-процесс уже работает под
учёткой пользователя → дублируем токен процесса в impersonation-токен,
`AccessCheck`/`AuthzAccessCheck` каждого SD-блоба из индекса против этого
токена. Вердикты папок кэшируются в рамках одного запроса (папок на порядки
меньше, чем файлов). **Deny по умолчанию**: нет SD / кривой SD / ошибка
проверки → строка скрыта.

**Граница при выдаче:** `ntfs_fetch` открывает файл по SMB под учёткой
пользователя — файл-сервер применяет реальный ACL, включая share-level ACL,
которой в индексе нет вовсе. Сталость DACL в индексе (между USN-событием и
поллингом) закрывается именно этим: худший случай — пользователю покажут
строку, но выдача файла завершится ACCESS_DENIED.

**Ограничения, принять осознанно:** share-ACL и dynamic Access Control
(Central Access Policies) в индексе не моделируются; поиск может показать то,
что через шину недоступно (перекрывается fetch-границей).

**Аудит:** `fetch_audit` фиксирует выдачи полностью. Логировать ли тексты
поисковых запросов — приватность против расследований (О-2, рекомендация:
хранить только счётчики по пользователю, без текстов запросов).

**Защита самого индекса:** база — концентрат метаданных всей сети: файл и
папка — только Users:R (плюс спец-ACE для WAL-файлов, см. §10), бэкап —
только на защищённое хранилище; `sd`-блобы наружу не отдаются.

## 9. Конфигурация и секреты

Три YAML (по одному на роль; у агента на каждом файл-сервере свой):

```yaml
# ntfs-agent (файловый сервер)
volumes:
  - volume_guid: "\\?\Volume{AAAAAAAA-....}\"
    unc_base: "\\\\fs01\\photo$"
    include: ["**"]
    exclude: ["**/~$*", "**/.thumbnails/**"]   # служебный мусор
hub:
  url: "http://zcode-srv:8733"
  # токен — из env NTFS_AGENT_TOKEN, НЕ в yaml (правила репозитория)
schedule:
  usn_poll: 30s
  full_rescan: 168h          # раз в неделю
  metadata_workers: 12
usn_journal_mb: 2048         # рекомендация fsutil; wrap → полный рескан
```

```yaml
# ntfs-hub (сервер ZCode)
db_path: "E:\\ARM_AI\\ntfs-index\\index.db"
listen: "<ip-сервера-zcode>:8733"  # LAN-интерфейс для батчей агентов; firewall:
                                   # входящий 8733 ТОЛЬКО с IP файл-серверов
# персональные токены агентов + пароль LDAP-бинда — env, НЕ в yaml
ad:
  ldap_url: "ldaps://dc01.corp.local:636"
  base_dn: "DC=corp,DC=local"
  bind_user: "CORP\\svc-ntfs-index"
  cache_ttl: 168h
tags:
  - pattern: "\\\\fs01\\photo$\\**\\предметка*\\**"
    tags: ["предметка"]
  - pattern: "\\\\fs01\\photo$\\**\\лук*\\**"
    tags: ["лук"]
  - pattern: "\\\\fs02\\docs$\\сертификаты\\**"
    tags: ["сертификаты"]
tombstone_retention: 720h
```

```yaml
# mcp-ntfs (пользователь ZCode)
db_path: "E:\\ARM_AI\\ntfs-index\\index.db"   # тот же файл, read-only
cache:
  ttl: 24h
  max_fetch_bytes: 209715200                   # 200 МБ
```

Секреты (токен агент→hub, пароль LDAP-бинда) — только env-переменные,
обёртки по образцу `mcp-*-run.cmd`; гигиена репозитория (пре-коммит скан,
плейсхолдеры в примерах) — без изменений.

## 10. Эксплуатация

- Установка: `ntfs-indexer --role=agent|hub` как сервис Windows (sc.exe /
  NSSM), авторестарт; `mcp-ntfs` — per-user stdio из
  `~/.zcode/cli/config.json` (конвенция репозитория, entry `ntfs`).
- **ACL-рецепт папки индекса** (точные icacls-команды — в deploy-гайде по
  образцу DEPLOY-WINDOWS.md; здесь принцип и развилка):
  - Вариант A (рекомендация): WAL-режим; на файл `index.db` — явный ACE
    Users:R (создаётся хабом один раз), на папку — наследуемый Users:M,
    чтобы читатели могли открывать/создавать `-wal`/`-shm` (read-only
    WAL-коннект обязан писать в `-shm`). Минус: пользователи технически
    могут создавать файлы в папке — приёмлемо на доверенном RDS-сервере.
  - Вариант B (проще ACL, хуже конкурентность): `journal_mode=DELETE` —
    читателям `-shm` не нужен вовсе, папка Users:R; хаб-транзакции получают
    краткий EXCLUSIVE-лок (батчи короткие — терпимо).
- Мониторинг: `ntfs_status`, `GET /healthz`, stderr-логи в файлы сервисов;
  алерт на возраст USN-курсора > N минут.
- `--selftest` у всех трёх ролей по образцу существующих бинарей: агент —
  чтение тома и отправка тестового батча в hub; hub — открытие БД, схема,
  запись/чтение; mcp — открытие БД read-only, AccessCheck на собственном
  SD, копирование тестового файла в кеш.
- **Deploy-гайд для админов** (обязательный артефакт v1; по образцу
  DEPLOY-WINDOWS.md, на русском, с точными командами) — разделы:
  1) подготовка: служебные учётки (LDAP-бинд; опционально gMSA для сервисов),
     firewall-правила (входящий 8733 только от файл-серверов);
  2) файл-сервер: `fsutil` — создание USN-журнала нужного размера,
     установка `ntfs-indexer --role=agent` сервисом (sc/NSSM), yaml + env
     токена, запуск, проверка (healthz хаба, рост счётчиков строк);
  3) сервер ZCode: папка индекса + icacls-рецепт (вариант A/B из этого
     раздела), установка `ntfs-indexer --role=hub` сервисом, инициализация
     БД (миграции при старте), env токенов/пароля, проверка;
  4) регистрация `mcp-ntfs` per-user в `~/.zcode/cli/config.json`;
  5) диагностика: wrap журнала, отказы READ_CONTROL, блокировки чтения,
     логи сервисов, `ntfs_status` / `GET /healthz`;
  6) чек-лист приёмки по критериям А-1…А-8.

## 12. Риски и открытые вопросы

| # | Риск/вопрос | Митигция/статус |
|---|---|---|
| Р-1 | USN wrap (журнал переполнен) → дыра в дельтах | детект по LowestValidUsn; полный рескан по расписанию + по факту wrap |
| Р-2 | «Создатель vs владелец»: файлы, созданные под elevation, имеют owner=Administrators | документированное ограничение NTFS; поле owner = единственный доступный прокси создателя |

| О-1 | Аутентификация agent→hub: токен+LAN-ACL (рекомендация) vs SSPI/NTLM | решение при имплементации |
| О-2 | Аудит поисковых запросов: полные тексты vs счётчики | рекомендация: счётчики (приватность), полные — только fetch |
| О-3 | Вариант A/B журнала SQLite (§10) | финал в deploy-гайде после нагрузочной пробы |
| О-4 | Ретеншн tombstones (draft: 30 дней) | уточнить у владельца |
| О-5 | Приоритеты v2 (анонимизация vs EXIF) | к планированию v2 |

## 13. Roadmap и критерии приёмки

### Этапность развёртывания v1: пилот → первый файл-сервер → продуктив

Пилот выполняется **на локальной машине ZCode** (та же, где уже развёрнуты
mcp-pg-readonly / mcp-mssql-readonly по DEPLOY-WINDOWS.md): все три роли —
агент, хаб, MCP — на одном компьютере, без сети и без продуктивных
файловых серверов; зона поражения нулевая. Агент работает с локальным томом
(MFT/USN читаются по тому целиком — это механика NTFS), но `include`-фильтр
ограничивает строки индекса тестовой папкой с заведомо размеченным
содержимым: кириллица, глубокая вложенность, файлы с разными ACL, живые
переименования/удаления в процессе проверки. AD-обогащение на пилоте
опционально. Так проверяются сразу все технически рискованные места:
чтение MFT и сборка путей, парсинг USN, AccessCheck на реальных SD,
FTS/GLOB по кириллице, кеш, envelope.

| Этап | Где | Что разворачиваем | Критерий перехода |
|---|---|---|---|
| Э-0 пилот | машина ZCode (всё локально) | все роли на одном компьютере: агент на тестовую папку локального тома, хаб + SQLite локально, `mcp-ntfs` в конфиге владельца ZCode | А-2, А-4…А-8 зелёные на тестовой папке; А-3 — на файлах с заведомо разными ACL; решения ИБ не требуются (токен агента в минимальном виде, даже на localhost) |
| Э-1 первый файл-сервер | FS01 (фото-архив) + машина ZCode | агент на первом продуктивном сервере (fsutil, сервис, персональный токен), сетевой путь батчей: firewall-правило 8733, LAN-маршрут, LDAP-обогащение в бою | первый полный скан терабатного масштаба прошёл (А-1 на реальном объёме); свежесть ≤60 с подтверждена; теги папок согласованы с владельцем архива |
| Э-2 продуктив | все файл-серверы | остальные агенты, финальные теги папок, аудит, deploy-гайд для админов (§10), приёмка А-1…А-8 целиком, регистрация `mcp-ntfs` аналитикам, учёт решений встречи ИБ (В-1…В-6) | чек-лист приёмки зелёный; согласование ИБ получено |

#### Э-0 по задачам: разведка → фундамент → снимок → дельты → права → поиск → инструменты

Декомпозиция построена так, что каждая задача закрывает одно техническое
неизвестное из §12 и опирается только на проверённое предыдущими задачами;
порядок не случаен: разведка до кода, схема базы до данных, снимок до дельт,
фильтр прав до выдачи файлов. Колонка «грабли» — план защиты, а не список
работ: у каждого подвоха уже прописана страховка.

| # | Задача | Содержание и критерий готовности | Что может пойти не так → страховка |

Грабли, специфичные для Э-1 (не пилота): агент ставится Windows-сервисом под
LocalSystem (автостарт и логи, а не «консоль у админа»); USN-журнал на
продуктивном томе может быть не активен — как на E: этой машины (П-3), его

первый скан терабайтного тома идёт часы — запускать по расписанию;
firewall — входящий 8733 только с IP файл-серверов.

## Приложение А. Глоссарий основных терминов

Для обсуждения логики со службой ИБ; самостоятельная версия для встречи —
`reports/2026-09-20_материал_встреча_ИБ_MCP_NTFS.md`.

### NTFS и USN-журнал

| Термин | Что это |
|---|---|
| **NTFS** | Файловая система Windows; метаданные каждого файла хранятся в служебных структурах тома |
| **MFT** (Master File Table) | Главная таблица файлов тома: одна запись = один файл или папка; перечисление MFT даёт весь том без обхода каталогов |
| **FRN** (File Reference Number) | 64-битный идентификатор записи MFT; стабильнее имени — переживает переименование и перемещение |
| **USN** (Update Sequence Number) | Монотонно растущий номер изменения на томе |
| **USN Change Journal** | Системный файл тома ($UsnJrnl), куда NTFS **сама** пишет запись о каждом изменении: создание, удаление, запись данных, переименование, смена ACL. Наша «лента событий» |
| **USN Record** | Одна запись журнала: FRN, FRN родителя, флаги причин, имя, номер USN |
| **Reason flags** | Причины события: `CREATE`, `DELETE`, `RENAME_OLD/NEW`, `DATA_OVERWRITE`, `ACL_CHANGE` и др. — по ним агент решает, что делать со строкой индекса |
| **Wrap журнала** | Переполнение журнала по кругу: старые записи затираются → в дельтах «дыра», нужен полный перескан; лечится размером журнала |
| **FSCTL_ENUM_USN_DATA / FSCTL_READ_USN_JOURNAL** | Управляющие коды DeviceIoControl: перечисление MFT (первичный скан) и чтение журнала с курсора (инкремент) |
| **Volume GUID Path** | `\\?\Volume{...}\` — стабильная идентификация тома, не зависящая от буквы диска |
| **Tombstone** | «Надгробие»: строка индекса с пометкой об удалении файла, хранится ограниченный срок |

### Безопасность Windows / AD

| Термин | Что это |
|---|---|
| **SID** | Идентификатор безопасности (S-1-5-…): пользователя, группы, компьютера; уникален в домене |
| **Owner SID** | Владелец файла, по умолчанию — создатель; при создании с повышенными правами (UAC) владельцем становится Administrators (риск Р-2) |
| **SD** (Security Descriptor) | Блоб безопасности объекта: Owner SID + Group SID + DACL + SACL; именно он сохраняется в индексе |
| **DACL** | Список, кто и что **может** делать с объектом (allow/deny-записи); «проверка прав» = сверка DACL с токеном |
| **SACL** | Список обращений, которые **логируются** системным аудитом (мы не используем) |
| **ACE** | Одна запись DACL: тип (allow/deny), маска прав, SID |
| **Access token** | Токен процесса: SID пользователя + группы + привилегии; MCP-процесс наследует токен самого пользователя |
| **AccessCheck** | Windows API: сверка токена с SD — локально, без сети |
| **FILE_READ_DATA / FILE_LIST_DIRECTORY / FILE_TRAVERSE** | Право читать файл / видеть содержимое папки / проходить сквозь папку; правило видимости: READ на файле + LIST на всех предках |
| **READ_CONTROL** | Право читать чужой SD — нужно индексатору для сбора DACL |
| **AD / LDAP / bind** | Active Directory; LDAP — протокол запросов; bind — служебная учётка подключения |
| **sAMAccountName / displayName / department** | Атрибуты AD: логин, ФИО, отдел — обогащение владельца в индексе |
| **LocalSystem** | Системная учётка сервиса-агента на файл-сервере (читает весь том — это его работа) |
| **SSPI / NTLM / Kerberos** | Механизмы встроенной Windows-аутентификации — вариант для канала агент→хаб |

### Сеть и доступ к файлам

| Термин | Что это |
|---|---|
| **SMB** | Протокол доступа к файлам по сети (шары `\\сервер\папка`) |
| **UNC-путь** | Канонический сетевой путь `\\fs01\photo$\...` |
| **Share-level ACL** | Отдельный слой прав на шару ПОВЕРХ NTFS-прав; в индексе не моделируется, применяется файл-сервером при выдаче |
| **UAC / elevation** | Контроль учётных записей; влияет на то, кем записывается владелец файла |

### Индекс и стек

| Термин | Что это |
|---|---|
| **SQLite** | Встраиваемая БД в одном файле; индекс лежит на локальном диске сервера ZCode |
| **WAL / `-wal` / `-shm`** | Режим журналирования SQLite: один писатель (хаб) + много читателей (MCP-процессы) без взаимных блокировок |
| **FTS5** | Полнотекстовый поиск SQLite (по именам файлов, понимает кириллицу) |
| **GLOB** | Поиск по маске `*паттерн*` — второй режим поиска наряду с FTS |
| **UPSERT / курсор / квитирование** | Идемпотентная запись «вставить или обновить»; USN-курсор — позиция в журнале; квитирование — хаб подтвердил батч, только тогда агент двигает курсор |
| **MCP / stdio** | Model Context Protocol; stdio — запуск сервера как процесса ZCode с обменом через stdin/stdout |
| **Envelope** | Формат ответа инструмента: метаданные (row_count, truncated, notice) до строк, кэпы 4000 строк / 48 КБ |

## Приложение Б. Физика процесса по шагам

### Контур 1 — индексация (фон, без пользователей)

1. **Развёртывание:** на каждом файл-сервере создаётся USN-журнал (`fsutil`)
   и ставится сервис-агент под LocalSystem; на сервере ZCode — хаб с SQLite
   на локальном диске.
2. **Первичный скан:** агент перечисляет MFT тома (`FSCTL_ENUM_USN_DATA`) —
   весь скелет: имена, FRN, родителей, атрибуты; миллионы записей ≈ минуты.
3. **Метаданные:** для каждой записи агент открывает файл по FRN и снимает
   размер, даты, owner SID, DACL-блоб (`GetSecurityInfo`) пулом воркеров в
   фоне. Содержимое файлов **не читается**.
4. **Сборка пути:** полный UNC-путь восстанавливается из цепочки FRN предков.
5. **Батч в хаб:** записи уходят по HTTP (токен); хаб в одной транзакции
   вставляет/обновляет строки, обновляет FTS, догружает профиль владельца из
   AD (LDAP по SID), вычисляет теги папок, запоминает USN-курсор и шлёт
   подтверждение — только после него агент считает батч обработанным.
6. **Режим ожидания:** раз в ~30 с агент читает журнал с последнего
   подтверждённого курсора: создание → вставка, удаление → tombstone,
   переименование → обновление пути, `ACL_CHANGE` → перевыгруз DACL. Индекс
   отстаёт от ФС максимум на интервал поллинга.
7. **Самоконтроль:** еженедельный полный рескан; при wrap журнала — немедленный.

### Контур 2 — клиентский путь (пользователь → файл в руках агента)

1. **Старт:** ZCode запускает `mcp-ntfs` под учётной записью вошедшего
   пользователя — процесс наследует **токен пользователя**, а не сервиса.
2. **Запрос:** агент (LLM) вызывает `ntfs_search` (паттерн/слова/фильтры).
3. **SQL-кандидаты:** read-only коннект к SQLite (WAL-ридер параллельно
   писателю), FTS/GLOB + фильтры — миллисекунды, локально.
4. **Фильтр доступа:** для каждой строки-кандидата — `AccessCheck` её
   сохранённого DACL против токена пользователя (READ на файл, LIST на всех
   предках, кэш вердиктов папок). Недоступное отбрасывается **молча**;
   ошибка проверки = скрыть.
5. **Выдача:** список в envelope + notice о свежести индекса по корням.
6. **Запрос файла:** `ntfs_fetch`; путь обязан резолвиться в строку индекса
   (анти-traversal), произвольные пути вне корней не принимаются.
7. **Жёсткая граница:** SMB-открытие UNC-пути **под учёткой пользователя** —
   файл-сервер применяет реальный NTFS ACL + share ACL; нет прав →
   ACCESS_DENIED даже при устаревшем DACL в индексе.
8. **Кеш:** потоковое копирование в `%LOCALAPPDATA%\Temp\mcp-ntfs\<сессия>\`
   (per-user по построению) с лимитом размера или preview-диапазоном;
   расхождение mtime → notice; факт выдачи — в `fetch_audit`.
9. **Анализ:** агент читает уже локальный файл штатными средствами —
   сетевого трафика на этом шаге нет.
10. **Очистка:** `ntfs_cache_clear` или TTL (24 ч).

Три тезиса для службы ИБ (разжёванная модель §8):

1. Индексатор не читает содержимое — только метаданные ФС и DACL; всё, что
   он собирает, ОС отдаёт любому субъекту с правом READ_CONTROL.
2. Выдача файла идёт под учёткой самого пользователя, а не сервисной —
   авторизация происходит штатным путём файл-сервера, «супер-доступа» нет.
3. Поиск не раскрывает недоступного: DACL-фильтр скрывает факт
   существования; при сбое фильтра выдачу остановит файл-сервер; кто/что/
   когда брал — в `fetch_audit`.
